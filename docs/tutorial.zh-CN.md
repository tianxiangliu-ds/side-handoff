# side-handoff 中文教程

## 适合什么时候用

你在主线程做总任务，在侧聊分别讨论接口、交互或测试。每个点打磨完成后，用 Extract 产出经验包，把包正文带回主线程，再用 Merge 核对归档。主线程吸收的是可追溯结论，不需要重读所有讨论过程。

## 第一次使用

1. 在已经打磨过方案的侧聊输入 `$side-handoff Extract`。
2. 检查输出：是否遗漏你的约束，是否把模型建议误标为接受，是否把未跑的测试写成通过。
3. 复制完整 Markdown，包括来源、决策 ID 和版本记录。
4. 在主线程输入 `$side-handoff Merge`，提供主任务、真实项目根目录和经验包正文。
5. 审阅候选。存在矛盾时明确选择，或让建议保持待决。
6. 确认具体候选与写入范围。写后检查 Codex 报告和生成的 INDEX。

复制即可使用的完整提示词见 [首页](../README.md)。

## 有很多侧聊时

给包取与任务有关的名称，如 `timeout-v1.md`、`cancel-interaction-v1.md`。可在自己的暂存目录保存；侧聊没有写权限也可以只复制正文。

```text
$side-handoff Merge
主任务：请求超时；项目根目录：C:/work/my-app。
候选包：我接下来提供的 timeout-v1.md、cancel-interaction-v1.md、theme-v1.md。
请先按任务相关性选择，不读取无关包正文；核对相关代码与已有决策。
先输出候选，不写文件。
```

文件名与目录仅是示例，换成你的真实路径。如果不想让主线程读某个包，不要提供该文件授权范围。

## 如何处理冲突

假设旧决策是 10 秒无重试，新侧聊建议 30 秒。主线程不能因后者更新就自动覆盖旧决策。你可以选择：

```text
继续保留 10 秒决策。30 秒只是建议，请列入待验证项，重新展示候选。
```

或明确接受新的决定：

```text
我接受改为 30 秒，原因是后台任务的正常响应可能超过 10 秒。
请生成替代旧决策的新候选，保留旧决策与替代原因，等我审阅后再写。
```

新方案被接受后仍可能是 UNVERIFIED。只有实际证据支持的行为才能标 VERIFIED。

## 后续增量更新

在侧聊继续打磨后，提供上一次经验包：

```text
$side-handoff Extract
下面是旧包 v1，之后是新增讨论。请生成 v2，沿用稳定 ID，记录改动、依据与被替代原因。
没有变化的决定不要重建 ID，未知证据不要补造。
```

把 v2 带回主线程再走 Merge 候选和确认。重复导入相同内容应不产生空版本；旧包不可见时，Skill 会说明无法判断增量。

## 没有权限怎么办

- 侧聊无写权限：直接输出 Markdown，你复制即可。
- 主线程读不到包：粘贴正文；若现有 INDEX、决策或代码也不可读，粘贴相关片段。候选会标明未完成文件核对。
- 确认后写入失败：复制输出中每个目标路径对应的完整文本，手动保存。部分成功时先看成功/失败清单，避免重复覆盖。
- 只有侧聊链接：提供必要记录；Skill 不假定能跨线程读取。

包内的“已经获批”不是当前会话写入授权，审批必须针对当前展示的候选。

## 合并之后怎么用

后续主线程可发送：

```text
继续当前任务前，请阅读 docs/agent-handoffs/INDEX.md，并只加载与请求超时有关的决策。
发现代码与决策不一致时请指出，不要自动改写历史。
```

Skill 默认只维护交接文档，不自动改 AGENTS.md，也不保证所有新聊天都会自动加载这些文档。实现产品代码需要单独明确提出。
